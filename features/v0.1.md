SPEC: Multi-tenant Jira → Multi-agent Orchestrator → GitHub PRs (+ Admin Dashboard)

Build a production-minded v1 service that lets multiple AI agents work from Jira issues across MANY different client Jira projects (“tenants”), producing GitHub pull requests and posting progress back to Jira.

High-level goals
- Jira is the source of tasks (client-facing).
- Service runs multi-agent workflow per issue (PM → Dev → Test → Review).
- Output is ALWAYS a GitHub PR + a Jira comment with summary + how to test.
- Strong tenant isolation: each client Jira/project has separate auth/config; never mix tenants.
- Safe-by-default: no auto-merge, minimal Jira mutations (labels/comments only by default).

Non-goals (v1)
- No auto-merge.
- No editing Jira issue descriptions/fields beyond labels/comments (unless explicitly enabled).
- No “agent runs on everything”—only run when explicitly queued.

========================================================
1) TECH CHOICES
========================================================
Language/runtime
- Python 3.11

Service framework
- FastAPI for HTTP API + webhook ingestion
- Background worker: asyncio task queue or APScheduler (simple). Must support concurrent runs across tenants with per-tenant concurrency limits.

Storage
- SQLite for v1 (with migrations), designed to swap to Postgres later

Frontend (Admin Dashboard)
- Simple React SPA served by FastAPI OR server-rendered templates.
- Keep it minimal, functional, not fancy.

AI orchestration
- Use OpenAI Agents SDK to define 4 agents:
  1) PM agent
  2) Developer agent
  3) Tester agent
  4) Reviewer agent
- Use tools for Jira (via MCP), GitHub API, local git, and local command execution.

Repo editing / “hands”
- Use local git worktrees/checkouts per run
- Developer agent uses a “Codex tool” interface that can:
  - propose edits
  - apply edits
  - run commands
  - read files
(Implement this as a tool wrapper; actual mechanics can be done via subprocess + file edits.)

========================================================
2) TENANT MODEL (MANY CLIENT JIRAS)
========================================================
Define “tenant” as: one client’s Jira context (Jira site + project keys) + allowed repos + policy.

Tenants are stored in DB and manageable via Admin Dashboard (not YAML in v1).

Tenant fields (DB)
- tenant_id (string, unique)
- name (string)
- is_enabled (bool)
- jira:
  - mcp_endpoint (string)  # tenant-specific MCP endpoint
  - auth_ref (string)      # reference to secret name (never store secrets in DB)
  - project_keys (json list of strings)
  - ready_label (default "agent:ready")
  - in_progress_label (default "agent:in-progress")
  - blocked_label (default "agent:blocked")
  - done_label (optional)
  - ready_jql (string)  # must be scoped to project_keys
  - webhook_secret_ref (optional secret ref)
- github:
  - mode: "github_app" (required)
  - app_id_ref (secret ref)
  - private_key_ref (secret ref)
  - webhook_secret_ref (optional)
  - installation_id (string/int)  # per tenant installation
- repos:
  - allowlist (json list of repo urls)
  - mapping_rules:
      - by_project_key (json map project_key -> repo_url)
      - by_component (optional json map component_name -> repo_url)
      - fallback_repo (optional repo_url)
- policy:
  - allow_jira_transitions (bool default false)
  - allow_pr_creation (bool default true)
  - allow_label_mutations (bool default true)
  - max_runtime_minutes (int default 30)
  - max_dev_test_review_loops (int default 2)
  - max_concurrent_runs (int default 2)
  - allowed_commands (json list, optional; can be per repo later)
  - require_agents_md (bool default false)

Tenant isolation requirements
- Every Jira call uses the tenant’s MCP connection.
- Every GitHub action uses the tenant’s GitHub App installation token and allowlisted repos only.
- Every run is tagged with tenant_id and must NEVER access other tenant configs.

========================================================
3) JIRA INTEGRATION (MCP) + WEBHOOKS
========================================================
Jira access must use MCP (no direct Jira REST client in v1).

Jira MCP required capabilities (discover at startup)
- search_issues(jql)
- get_issue(issue_key) including: summary, description, labels, components, comments
- add_comment(issue_key, markdown)
- add_labels(issue_key, labels[])
- remove_labels(issue_key, labels[])
Optional capability
- transition_issue(issue_key, transition) (only used if tenant policy allows)

Capability discovery & mapping
- On tenant initialization, discover tool names and map them to the above capability interface.
- If required capability missing: tenant is disabled and admin sees “missing capability” error.
- If optional missing: transitions remain disabled regardless of config.

Webhook ingestion (required)
- Implement POST /jira/webhook
- Must route to correct tenant:
  - Either: include tenant_id in webhook URL (recommended): /jira/webhook/{tenant_id}
  - Or: infer from projectKey / baseUrl mapping (riskier).
- Verify authenticity:
  - If Jira webhook supports secret token: validate against tenant webhook_secret_ref
  - If not available: use network allowlist / auth proxy (documented), and still validate payload shape.

Webhook event handling
- Only enqueue when:
  - issue has ready_label present
  - issue is not already locked/running
- Handle idempotency: multiple webhook deliveries must not create duplicate runs.
- Log request_id + tenant_id + issue_key.

Fallback poller (optional, disabled by default)
- `python -m orchestrator poll --tenant all` runs ready_jql per tenant
- Useful if client cannot configure webhooks

========================================================
4) GITHUB INTEGRATION (GITHUB APP) + LOCAL GIT
========================================================
Use GitHub API (NOT MCP) plus local git for commits/push.

Auth: GitHub App (required)
- Use app_id + private_key to mint JWT
- Exchange for installation access token for tenant installation_id
- Tokens are short-lived; generate per operation and cache briefly in memory.

Repo access rules
- Enforce tenant repo allowlist BEFORE cloning/pushing/creating PR.
- If repo not allowlisted: fail run, comment Jira, mark blocked.

Git operations
- For each run:
  - Create isolated workspace dir:
    /workspaces/{tenant_id}/{issue_key}/{run_id}/
  - Clone repo (or reuse cache) into workspace
  - Create branch:
    branch name template: "jira/{issue_key}-{slug}"
  - Use git worktree if preferred, but isolation must be guaranteed.
  - Commit message: "{issue_key}: {summary}"

PR creation
- Open PR against default branch
- PR title: "{issue_key}: {issue summary}"
- PR body includes:
  - summary
  - acceptance criteria checklist
  - how to test
  - any caveats

No auto-merge
- Never merge. Never enable auto-merge.

========================================================
5) RUN QUEUE, LOCKING, IDEMPOTENCY
========================================================
DB tables (minimum)
- tenants
- runs:
  - run_id (uuid)
  - tenant_id
  - issue_key
  - repo_url
  - branch
  - pr_url
  - status: queued | running | succeeded | failed | blocked
  - created_at, started_at, finished_at
  - last_error (text)
  - plan (text/json)
- locks (optional if using labels + runs table):
  - tenant_id, issue_key, run_id, locked_at

Locking strategy (must be safe across concurrent webhook deliveries)
1) Check DB: if a run is active for {tenant_id, issue_key} in queued/running -> ignore
2) Acquire Jira “lock” via labels:
   - add in_progress_label
   - remove ready_label
   - If this fails, do not proceed
3) Write run row to DB and mark running

On completion
- remove in_progress_label
- optionally add done_label (config)
On failure
- add blocked_label
- keep in_progress_label removed
- add Jira comment explaining failure + what human should do next

========================================================
6) MULTI-AGENT WORKFLOW (PM → DEV → TEST → REVIEW)
========================================================
Inputs
- Jira issue: summary, description, comments, components, labels
- Repo rules:
  - If AGENTS.md exists in repo root, load and provide to agents as “project rules”.
  - Else provide default rules (below).

Default repo rules (apply if no AGENTS.md)
- Keep diffs minimal; avoid unrelated refactors.
- Prefer small, reviewable commits (but ok to do 1 commit in v1).
- Must run tests before PR (as configured/allowed).
- Never add secrets.
- Do not modify CI/CD config unless required by task.
- Document how to test in PR + Jira comment.

Agent roles & required outputs

PM agent
- Reads Jira issue and produces:
  - plan (3–8 steps)
  - acceptance criteria checklist
  - risk/unknowns
  - suggested test commands
- Posts Jira comment: “Plan” with plan + criteria
- Stores plan in DB

Developer agent
- Implements changes in repo to satisfy acceptance criteria
- Uses only allowed commands and allowed repos
- Produces:
  - code changes
  - commit(s)

Tester agent
- Runs tests (from AGENTS.md or tenant allowed_commands/default)
- If failing:
  - propose fixes
  - loop back to Developer agent
- Ensures minimal test coverage added/updated where appropriate

Reviewer agent
- Reviews diff for:
  - correctness vs acceptance criteria
  - edge cases
  - security/PII
  - style consistency
- If changes requested:
  - loop back to Developer (max loops = tenant policy max_dev_test_review_loops)
- Produces final “review summary” for Jira/PR

Completion steps
- Push branch
- Open PR
- Post Jira “Final” comment containing:
  - PR link
  - summary of changes
  - how to test
  - any known limitations
- Mark run succeeded in DB

Failure handling
- Post Jira comment: what failed + logs excerpt (safe) + next steps
- Mark run failed/blocked in DB
- Add blocked_label

========================================================
7) TOOLING / GUARDRAILS
========================================================
Command execution guardrails
- Implement an allowlist of commands (tenant-level for v1):
  - Examples: "pytest", "npm test", "mvn test", "gradle test", "pnpm test", "ruff", "black", etc.
- Deny dangerous patterns:
  - "rm -rf", "curl | sh", "wget | sh", "sudo", "chmod 777", etc.
- Capture stdout/stderr to DB (trim) and structured logs.

Repo allowlist guardrail
- Enforce tenant repo allowlist before:
  - cloning
  - pushing
  - PR creation

Data leakage guardrail
- Never copy content between tenants
- Never include secrets in Jira comments or PRs
- Logs must redact tokens and auth headers

Runtime limits
- Per run: max_runtime_minutes
- Per tenant: max_concurrent_runs

========================================================
8) ADMIN DASHBOARD + ADMIN API
========================================================
Admin UI requirements
- Route: /admin
- Features:
  - List tenants
  - Add tenant
  - Edit tenant
  - Enable/disable tenant
  - Show tenant health (MCP capability check + GitHub install token check)
  - View runs (filter by tenant/status/date)
  - View run details: plan, PR URL, last error, timestamps

Admin API endpoints
- GET  /api/admin/tenants
- POST /api/admin/tenants
- GET  /api/admin/tenants/{tenant_id}
- PUT  /api/admin/tenants/{tenant_id}
- POST /api/admin/tenants/{tenant_id}/test-jira
- POST /api/admin/tenants/{tenant_id}/test-github
- GET  /api/admin/runs?tenant_id=&status=&from=&to=
- GET  /api/admin/runs/{run_id}

Admin auth
- v1 simplest acceptable:
  - One admin password via env var (HTTP Basic or session)
  - OR recommend running behind an auth proxy (Cloudflare Access / Google IAP) with a config note.
- Do not expose admin endpoints without auth.

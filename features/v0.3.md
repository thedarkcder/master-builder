CHANGE: Human-gated workflow using a “Ready for Agent” column/status

========================================================
1) HUMAN GATE (PRIMARY CONTROL)
========================================================
Principle:
- Agents MUST ONLY start work when a human moves an issue into the “Ready for Agent” status/column.
- Agents MUST NOT work on issues in “To Do”, “Backlog”, or any non-ready state.

Tenant config additions:
- jira:
    - ready_statuses: ["Ready for Agent"]  # allow list; per tenant
    - ready_jql must include ready_statuses AND exclude Done:
        e.g. project in (...) AND status in ("Ready for Agent") AND statusCategory != Done

Queue rule (hard requirement):
- An issue is eligible if:
  - status in tenant.ready_statuses
  - NOT already locked/running
  - NOT statusCategory = Done
- Labels are optional. Status is the main gate.

Locking rule:
- On pickup, agent adds label "agent:in-progress" (optional but recommended) for visibility/locking.
- Agent does NOT change status by default.
- If label mutation not allowed by tenant policy, use DB lock only.

========================================================
2) JIRA WEBHOOK TRIGGER
========================================================
Webhook routing:
- Trigger enqueue when:
  - issue transitioned into a ready_status (“Ready for Agent”)
  OR
  - issue updated and is currently in a ready_status (idempotent re-check)

Idempotency:
- Multiple webhooks must not create duplicate runs for the same issue.

========================================================
3) AGENTS CAN CREATE BUGS/ISSUES, BUT NEVER AUTO-QUEUE THEM
========================================================
Allow agents to create Jira issues via MCP when needed:
- Examples:
  - “Bug found during testing”
  - “Tech debt follow-up”
  - “Missing acceptance criteria / requirement clarification”
  - “Add tests later” (if genuinely out of scope)

Rules for agent-created issues:
- Created issues MUST land in the default backlog / To Do status (or whatever Jira default is).
- Agents MUST NOT move issues into ready_status automatically.
- Agents MUST add a short template to the issue:
  - What was found
  - Impact
  - Steps to reproduce (if bug)
  - Suggested fix
  - Link to originating issue + PR

Optional (recommended) visibility:
- Post a Discord message in the tenant channel:
  - “Created follow-up issue: ABC-456 (Bug) — needs human triage”
- Comment the original Jira issue with the created issue link.

========================================================
4) DISCORD MESSAGING UPDATE
========================================================
Discord should reinforce the human gate:
- When someone asks in Discord “why didn’t it run?”, bot replies:
  - “This system only runs items moved to ‘Ready for Agent’. Move the Jira issue to that status to queue it.”

========================================================
5) ADMIN DASHBOARD UPDATE
========================================================
Tenant admin screen must include:
- Ready statuses list (multi-select string list)
- A “Preview JQL” / “Test ready query” action showing which issues are eligible right now
- Run history by tenant

========================================================
A) REPO BOOTSTRAP: ensure .codex exists per repo
========================================================
Requirement:
- For every target repo, the system MUST ensure a .codex/ directory exists.
- If missing, it must create it on the working branch for that issue (or on a dedicated bootstrap PR), containing:
  1) .codex/OPERATING.md  (how Codex/agents should work in this repo)
  2) .codex/POLICY.md     (guardrails; what agents must/ must not do)
  3) .codex/skills/       (reusable “skills” instructions)
  4) Optional: AGENTS.md at repo root if not present (or reference it from .codex/OPERATING.md)

Bootstrap behaviour:
- If .codex is missing, create it and include it as part of the PR for the first ticket worked in that repo.
- If the current ticket is sensitive and adding .codex is undesirable, open a separate “Bootstrap .codex” PR first, then proceed.
- Store in DB whether repo has been bootstrapped so we don’t repeat work unnecessarily.

Required files content (templates):

.codex/OPERATING.md
- Purpose: “How agents operate in this repo”
- Must include:
  - Repo overview (short)
  - Allowed commands (tests/lint/build) and exact commands
  - How to run locally and in CI
  - Branch/PR conventions
  - Where to add tests
  - Definition of Done checklist
  - Link to .codex/POLICY.md

.codex/POLICY.md (this is the “adhere to policy” file)
- Must include:
  - Do not add secrets, tokens, credentials, API keys
  - Do not exfiltrate customer data; no copying data into issues/PRs
  - Keep diffs minimal; no unrelated reformatting
  - No dependency upgrades unless required
  - No auto-merge; PR must be reviewed by a human
  - Commands restricted to allowlist; no destructive shell commands
  - If uncertain, stop and mark ticket blocked with next steps

.codex/skills/ (skills are plain markdown files; each describes a repeatable workflow)
Minimum skills to create:
- .codex/skills/run_tests.md
  - “Run tests: <commands>”
  - “If failing, capture output and fix”
- .codex/skills/add_tests.md
  - “When changing logic, add/update tests”
  - “Prefer unit tests; add integration tests if required”
- .codex/skills/pr_checklist.md
  - “PR must include: summary, how to test, risks, rollback notes if relevant”
- .codex/skills/security_sanity.md
  - “Check for secrets, unsafe logging, auth bypass”
  - “No PII in logs or comments”

Agent enforcement:
- Before any code changes, agents must read:
  - .codex/POLICY.md (required)
  - AGENTS.md if present (preferred), else .codex/OPERATING.md
- The orchestrator must inject these docs into the agent context as “must-follow rules”.

========================================================
B) DISCORD INTEGRATION: channel per project + notifications
========================================================
Goal:
- For each tenant (client/project), automatically create (or reuse) a Discord channel in your server.
- Use that channel as the human-facing feed:
  - ticket picked up
  - plan posted
  - progress updates
  - PR opened / PR ready for review
  - failures / blocked with next steps

Discord approach:
- Implement a Discord Bot (discord.py) with required permissions:
  - Manage Channels (create channels)
  - Send Messages
  - Read Message Content (only if we enable Discord -> ticket creation)
- Bot runs as part of the service (same Docker container) or as a sidecar process.

Discord configuration (env + DB):
- DISCORD_BOT_TOKEN (secret)
- DISCORD_GUILD_ID (server id)
- DISCORD_CATEGORY_ID (optional: create channels under a category)
Tenant fields:
- discord:
  - channel_id (nullable; stored after creation)
  - channel_name_template: "proj-{tenant_id}" (default)
  - notify_events: [ "run_started", "plan_posted", "pr_opened", "run_failed" ] (default all)

Channel creation rules:
- On tenant creation OR first webhook event for that tenant:
  - If no channel_id, create channel using template, store channel_id in DB.
- If channel already exists by name, reuse it and store id.

Messages format:
- Use short structured messages with:
  - tenant name
  - issue key + title
  - run_id
  - current stage (PM/DEV/TEST/REVIEW)
  - links: Jira issue link + PR link when available

Notify “PR ready”:
- When PR is opened (or when Reviewer agent completes), post:
  - ✅ PR Ready: <PR URL>
  - Summary of changes
  - How to test
  - Any risks / notes
- Also include a checklist of acceptance criteria.

========================================================
C) DISCORD -> WORK ITEMS (optional but requested)
========================================================
Optional feature:
- In each tenant Discord channel, allow you to type new work requests like:
  - “feature: add X”
  - “bug: fix Y”
  - “test: add coverage for Z”
These messages should create Jira issues (or add subtasks) in the tenant’s Jira project.

Implementation:
- Enable via tenant.discord.allow_create_issues = false by default.
- If enabled:
  - Parse message prefix (feature/bug/test)
  - Create Jira issue via Jira MCP (create_issue capability) IF available.
  - If create_issue is not available in MCP, then:
    - Post back: “Cannot create issues via MCP; please create in Jira and label agent:ready”
- After creating the issue, bot replies with the Jira issue key and link.
- The issue is NOT auto-queued unless the message includes “queue” or you add the label agent:ready.

Safety:
- Only allow issue creation from a Discord allowlist of user IDs (admin list in env/DB).
- Always echo back what will be created and keep descriptions concise.

========================================================
D) WEBHOOK FLOW: push updates to Discord + Jira

- After PR open: post “PR ready” to Discord and Jira
- On failure: post error summary + next steps to Discord and Jira

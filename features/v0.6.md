========================================================
1) “GOOD TO DO” VALIDATION CHECKLIST (MUST PASS BEFORE CODING)
========================================================
Before any execution run (PM/Dev/Test), the PM agent MUST validate the issue is “Good To Do”.
If validation fails, the run MUST STOP EARLY and request clarification (Jira + Discord), and mark the issue as blocked.

Good To Do (GTD) requires:
A) Problem clarity
- Clear objective in 1–2 sentences: “What outcome are we trying to achieve?”
- Scope boundaries: “In scope” and “Out of scope” bullets (at least 2 each if non-trivial)
- Acceptance criteria checklist present (or PM agent must author it and ask for confirmation)

B) Context
- Affected component/service/repo is identifiable (via Jira components or repo mapping)
- Link to any relevant docs, endpoints, screens, or prior issues (if available)
- Expected user/business impact stated (even short)

C) Testability
- A “How to test” section exists OR PM agent proposes one
- For UI: specify expected behavior / states / error handling

D) Non-functional requirements (NFRs) (explicit decision)
- At minimum: one of the following is explicitly stated or chosen by Decision Gate:
  - MVP/quick test: minimal infra, simpler design acceptable
  - Scale-ready: design must support high throughput, resilience, observability, etc.
- If NFRs not stated and could materially change design, trigger Decision Gate (below).

E) Dependencies and risks
- External dependencies listed (APIs, DB schema, queues)
- Any migrations/rollouts noted (if applicable)

If GTD fails:
- Post “Clarification Required” comment with:
  - what’s missing
  - specific questions
  - recommended options (MVP vs scale-ready)
- Post Discord short signal summary
- Mark run status = blocked; add Jira blocked_label (and/or leave in To Do but comment clearly)

========================================================
2) DECISION GATE (BA/PM MODE) — DISCUSS BEFORE WORK STARTS
========================================================
Trigger Decision Gate when:
- Requirements are ambiguous or conflicting
- The design choice materially changes cost/complexity/architecture
- NFRs (performance, security, reliability, compliance, data retention) might change design
- There’s a trade-off: “quick MVP” vs “scale to millions” vs “enterprise compliance”
- The agent would otherwise guess or implement placeholders

Decision Gate behavior:
- PM agent must STOP and ask explicit questions BEFORE Dev begins.
- Questions must be framed like a BA/PM:
  - Impact, trade-offs, constraints, rollout, future-proofing
- Tag the right people/groups in comments:
  - Jira: use @mentions if supported; else prefix tags like “[NEEDS-PM]” “[NEEDS-BA]” “[NEEDS-SECURITY]”
  - Discord: ping a configured role (e.g., @Product, @Engineering) if available; otherwise @you

Decision Gate comment template (Jira + Discord summary):
- “Decision required before build”
- Options table:
  - Option A: MVP quick test (pros/cons, time/complexity, risks)
  - Option B: Scale-ready (pros/cons, complexity, risks)
- Specific questions (max 5)
- Recommendation (one line)

Hard rule:
- Dev agent MUST NOT start coding until Decision Gate is resolved, when triggered.

========================================================
3) NO PLACEHOLDERS / NO “ASK TO IMPLEMENT LATER” RULE
========================================================
Agents must not leave placeholder implementations, TODO stubs, or “dummy returns” unless explicitly approved.

Prohibited:
- “TODO: implement later” without a tracked issue
- placeholder classes/methods that compile but don’t function
- UI elements that are stubbed without behavior
- returning mock data in production paths

If partial work is unavoidable:
- Create a Jira issue in Backlog:
  - type: “Implementation follow-up”
  - include exact file paths and what remains
- Mark current run as blocked and request approval, OR
- Limit PR to non-functional scaffolding ONLY if ticket explicitly asks for scaffolding.

Reviewer agent MUST block PR if:
- placeholder code exists without linked Jira issue
- behavior is incomplete vs acceptance criteria
- any “temporary” code is in production path

========================================================
4) SIGNAL-ONLY OUTPUT FORMATTING (PR READY → DISCORD → JIRA)
========================================================
A) PR READY DISCORD MESSAGE (signal-only)
Post when PR is opened and review agent finishes initial pass.

Format:
- ✅ PR Ready: <PR link>
- Jira: <issue link> | Run: <run_id>
- What changed (3 bullets max)
- Risk/Impact (2 bullets max)
- How to test (3 steps max)
- Questions (only if Decision Gate items remain)
- Next action: “Please review + merge” / “Please answer questions”

B) JIRA FINAL COMMENT (more detail, still concise)
Format:
- PR: <link>
- Summary:
  - bullet list of changes
- Acceptance criteria:
  - checklist with ✅/⚠️/❌
- How to test:
  - commands + steps
- Notes:
  - migrations/rollout
  - monitoring/logs
- Open questions (if any)
- Follow-up issues created (Backlog): list links

C) Review agent PR comment (structured)
- ✅ Good
- ⚠️ Risks / edge cases
- ❌ Must-fix
- 🧪 Tests
- ❓ Questions for PM/BA (Decision Gate style)

Noise reduction:
- Do not paste logs unless necessary; if necessary, include max 10 lines and attach as file if supported (otherwise summarize).
- Prefer links over long text.

5) POLICY PACKS (per language) + BANNED PATTERNS
========================================================
Each repo must include or be bootstrapped with:
- .codex/policy_pack.json
- .codex/ENGINEERING_STANDARDS.md

Reviewer must enforce banned_patterns from policy_pack.json and block PR if present.

--------------------------------------------------------
5.1 Java/Spring policy pack (template)
--------------------------------------------------------
policy_pack.json (Java/Spring)
- test_commands:
  - mvn test  (or ./mvnw test if present)
- lint_commands (if present):
  - mvn -DskipTests=false checkstyle:check (only if configured)
- preferred patterns:
  - State machines for workflows (enum states + transition function)
  - Event-driven: Spring events or messaging; idempotent handlers
  - Dependency injection; interfaces at boundaries
  - Avoid static singletons; avoid God services
- banned_patterns:
  - Thread\\.sleep\\(
  - TimeUnit\\.SECONDS\\.sleep\\(
  - while\\s*\\(true\\)
  - catch\\s*\\(Exception\\s+e\\)\\s*\\{\\s*\\}   (swallow)
  - System\\.out\\.println
- guidance:
  - For waiting on async results, use:
    - CompletableFuture timeouts
    - message-driven callbacks
    - scheduled retries with backoff + state persistence

--------------------------------------------------------
5.2 Node policy pack (template)
--------------------------------------------------------
policy_pack.json (Node)
- test_commands:
  - npm test (or pnpm test/yarn test depending on lockfile)
- preferred patterns:
  - async workflows: event emitters, queues, durable job processors
  - explicit state machines (simple reducer-based) over ad-hoc timers
  - structured logging (pino/winston)
- banned_patterns:
  - setTimeout\\(
  - setInterval\\(
  - await\\s+new\\s+Promise\\(.*setTimeout
  - while\\s*\\(true\\)
- allowed exceptions:
  - setTimeout only for genuine scheduling (not sync), must be documented
  - tests can use fake timers (jest.useFakeTimers) rather than real waits

--------------------------------------------------------
5.3 React policy pack (template)
--------------------------------------------------------
policy_pack.json (React)
- test_commands:
  - npm test (or pnpm test)
  - optional: npm run test:ci
- preferred patterns:
  - UI state management: useReducer for complex flows (state machine style)
  - React Testing Library: test behavior, not implementation
  - async: findBy*/waitFor with timeouts
- banned_patterns:
  - setTimeout\\(
  - await\\s+new\\s+Promise\\(.*setTimeout
- testing rules:
  - Must add/update tests for behavior changes
  - Use MSW for network mocking if present
  - No fragile selectors; prefer getByRole/findByRole

--------------------------------------------------------
5.4 Python policy pack (template)
--------------------------------------------------------
policy_pack.json (Python)
- test_commands:
  - pytest
- preferred patterns:
  - pure functions for core logic
  - explicit state models (dataclasses/pydantic) for workflows
  - dependency injection via parameters (where reasonable)
- banned_patterns:
  - time\\.sleep\\(
  - while\\s*True\\:
- testing:
  - pytest with fixtures
  - monkeypatch / responses for external calls
  - no real network in unit tests

6) AGENT PROMPTING UPDATES (ENFORCEMENT)
========================================================
Orchestrator must inject into every run:
- policy_pack.json
- ENGINEERING_STANDARDS.md
- “Good To Do checklist”
- Decision Gate rules
- No Placeholders rule

The system prompt to Dev/Reviewer must include:
- “Do not use sleeps/timeouts for synchronization.”
- “If requirements/design trade-offs affect architecture (MVP vs scale), trigger Decision Gate and STOP.”
- “Do not leave placeholders; if partial needed, create Backlog issue and mark blocked.”

========================================================
7) FOLLOW-UP ISSUE CREATION RULES
========================================================
Agents may create Jira issues in Backlog for:
- Bugs found during review/testing
- Clarifications needed (Decision Gate follow-ups)
- Non-functional improvements discovered

But never auto-promote to To Do.
The created issue must include:
- Why it matters
- Impact
- Suggested approach
- Links to PR/original issue

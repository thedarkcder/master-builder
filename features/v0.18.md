# v0.18 - Ask GitHub Context + GitHub Webhook Reliability

## Objective
Make Discord `/ask` answers code-aware for staging review questions, and harden GitHub webhook handling so reviewer signals do not fail at runtime.

## What Changed
- `/ask` now includes scoped GitHub context from active project repositories.
- GitHub context now includes:
  - `open_pull_requests`
  - `staging_pull_requests` (subset where `base_ref == "staging"`)
- Ask intent planning and ask answer generation both receive GitHub context payloads.
- GitHub app client now supports listing open PR summaries for a repository.
- Fixed GitHub webhook reviewer signal mapping regression:
  - migrated from stale fields (`gate/status/summary`) to current signal contract (`ready/state/message`).

## Why
- Previously `/ask` relied mostly on Jira issue/status context and could not ground “review staging vs tickets” questions in actual PR state.
- GitHub webhooks were received but could 500 during reviewer signal handling because of a contract mismatch.

## Scope
### In scope
- Discord ask enrichment for GitHub PR context.
- Staging-targeted PR partitioning for ask context.
- GitHub webhook reviewer-signal contract compatibility fix.

### Out of scope
- Full branch diff ingestion into ask answers.
- Automatic Jira issue creation/remediation from GitHub review findings (tracked separately).

## Validation Notes
- Ask context tests updated to assert GitHub context is passed through to planner/answer stages.
- GitHub app tests added for open PR listing and payload validation.
- Webhook processing regression verified against reviewer-signal contract.

## Follow-up
- Add dedicated operational command/flow for explicit “compare staging branch against tickets” diff analysis.
- Add normalized finding contract for PR review failures/comments to optionally open Jira defects and enqueue remediation runs under policy.

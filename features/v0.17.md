# v0.17 - Jira-Driven Release Train Automation

## Objective
Automate release selection so teams do not manually set `Fix Version`.
When an issue moves to `Ready to Release`, the platform should assign it to the next release train automatically, and mark issues `Done` automatically when that release ships.

## Why
- Manual release tagging in Jira is error-prone and slow.
- Teams need predictable release grouping with auditability.
- Tenant onboarding should provision this behavior by default.

## Scope
### In scope
- Release-train service in orchestrator.
- Auto-assignment of Jira issues to next release on transition to `Ready to Release`.
- Tenant bootstrap flow that provisions Jira automation/webhook config for release-train events.
- Release manifest tracking (release version -> issue keys -> PRs/commits).
- Auto-transition Jira issues to `Done` after GitHub release tag is published.

### Out of scope
- Manual release-manager spreadsheets.
- Per-team custom Jira workflows beyond supported status mapping.
- Auto-merging PRs.

## Proposed Flow
1. Issue transitions to `Ready to Release`.
2. Jira automation/webhook calls orchestrator release API.
3. Orchestrator computes next release version from Git tags/policy.
4. Orchestrator links issue to that release version and stores manifest.
5. Release pipeline builds release branch/candidate from manifest.
6. On publish of release tag (`vX.Y.Z`), orchestrator transitions included Jira issues to `Done` and posts release comment.

## Tenant Bootstrap Requirements
When a new tenant is created and connections are validated:
- Create/update required Jira automation rule(s) for `Ready to Release`.
- Register tenant webhook endpoint(s) for release events.
- Validate required statuses exist (`Ready to Release`, `Done`).
- Run a dry-run verification and persist result in tenant setup report.

## Acceptance Criteria
- Transitioning an issue to `Ready to Release` triggers assignment to a computed next release without manual `Fix Version` editing.
- Orchestrator stores a deterministic release manifest that can be queried by release version.
- Publishing a GitHub release tag transitions manifest-linked issues to `Done`.
- Tenant setup provisions release automation for new tenants with a single setup flow.
- If tenant Jira permissions are insufficient, setup fails with actionable error and tenant is marked blocked for release automation.

## API / Integration Notes
- Add tenant admin endpoint: `POST /api/admin/tenants/{tenant_id}/release-automation/bootstrap`
- Add release ingest endpoint: `POST /api/releases/events/{tenant_id}`
- Add release manifest endpoint: `GET /api/admin/releases/{tenant_id}?version=vX.Y.Z`

## Decision Gate Triggers
- Release versioning policy ambiguity (patch-only vs minor cadence).
- Mixed repo release trains (single train vs per-repo trains).
- Jira permission model differences across tenants.

## Good To Do Checklist
- Jira status mapping for tenant includes `Ready to Release` and `Done`.
- GitHub tag naming policy confirmed.
- Tenant has valid Jira and GitHub credentials.
- Release cadence policy is defined (for example: weekly minor, ad-hoc patch).
